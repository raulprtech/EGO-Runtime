# G1.15 — explicit conversation execution authority

## Outcome

EGO now has a separate trusted path from an approved conversational plan to
the existing host-run loop. Approval remains non-executing. A second exact
human turn is required, Nigma revalidates the approval before issuing an
invocation, and terminal execution is projected to ARIA as informational
evidence rather than assistant text.

This increment implements and tests the authority core only. It does not
execute the real G1.14 plan and does not yet extend the Hermes supervisor to
observe the second phrase; that deployment adapter is G1.16.

## Contract

After `nigma.trusted-conversation-decision-record/v1`, EGO returns
`nigma.conversation-execution-authorization/v1` containing:

- exact execution phrase and SHA-256;
- exact plan and approval identities/digests;
- the approval expiry;
- `human_action_required=true`;
- `execution_performed=false`.

The phrase is shown through `nigma.decision-event/v2`. EGO separately stores
`nigma.conversation-execution-challenge/v1` as an atomic owner-only file. It
contains only sealed identities, hashes and timestamps, never raw phrase,
conversation reference, message reference or credentials.

`POST /v1/runtime/nigma/conversation-executions` requires the runtime token,
the independent human-decision token and an exact
`nigma.trusted-conversation-execution/v1` turn. It verifies:

1. preparation and interface identities/digests;
2. approval identity and digest;
3. fixed interface profile;
4. the same domain-separated conversation hash;
5. byte-exact execution phrase;
6. observation and approval expiry windows.

The host derives learner context from domain-separated hashes and a fixed
idempotency key from the sealed challenge. Repeated exact delivery therefore
maps to one host-run identity. The existing host loop still asks Nigma for an
approval-derived invocation, routes only the sealed runtime and records the
terminal receipt.

On success EGO emits `nigma.trusted-conversation-execution-record/v1` and a
single `nigma.execution-event/v1` titled `Ejecución finalizada`. Both report
`execution_performed=true`; the event feed remains read-only.

## Safety and compatibility

- Approval cannot implicitly invoke `host-runs`.
- A modified phrase, profile, conversation or sealed link fails before a
  host-run record exists.
- The normal runtime token alone cannot use the endpoint.
- The phone receives neither runtime nor human-decision credentials.
- Existing G1.13/G1.14 `nigma.decision-event/v1` records remain readable.
- Raw learner, phrase and conversation values are absent from the execution
  challenge.
- Real execution, model calls, external network, VPS, APK and Hermes source
  changes were zero.

## Retained failures and repairs

1. The sandboxed patch helper failed because `bubblewrap` is unavailable.
   Approved interactive `apply_patch` was used.
2. The first focused test command selected Hermes' Windows npm shim, whose Node
   executable is unavailable in WSL.
3. Calling the Linux npm path alone still failed because child shebangs could
   not resolve Node. A bounded Linux `PATH` repaired execution.
4. Two sidecar fixtures lacked the new authorization object and one event
   assertion expected v1 copy. The fixtures and assertion were migrated.
5. The repository has no `typecheck` script. The installed compiler was run
   directly with `npx tsc --noEmit`.
6. Vite briefly warned that its development WebSocket port was already in use
   during the first failed focused run; it did not affect the HTTP test and was
   absent from the passing runs.

## Remaining work

G1.16 must extend the replaceable Hermes sidecar with an execution binding and
restart-safe watcher. It must consider only a later exact human turn, call the
new endpoint once, seal terminal evidence and preserve the same transient-error
and expiry rules. Only after isolated proof should the owner be asked to send
the real second phrase from ARIA.
