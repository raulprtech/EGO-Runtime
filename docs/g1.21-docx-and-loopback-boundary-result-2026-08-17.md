# EGO G1.21 — DOCX and Windows/WSL host boundary

EGO now stages and extracts modern DOCX with the exact OpenXML media type. The
capability manifest declares `documents.docx`, Nigma handoff inference accepts
`.docx`, and execution uses local Mammoth raw-text extraction under the same
size, hash, root-containment and context limits as existing artifacts. Legacy
binary `.doc` remains fail-closed.

The change followed a real mobile diagnosis: EGO had correctly staged PDFs in
WSL, while Windows Hermes attempted to open the Linux reference and later could
not call EGO because its non-loopback HTTP URL was rejected. Hermes now reaches
this runtime through a Windows loopback-only proxy and treats the material URI
as opaque. EGO's private `.ego-materials/` is Git-ignored.

Verification used no private document contents. A synthetic OOXML fixture was
extracted successfully; focused material/DOCX tests passed 7/7, the full suite
passed 74 tests with one cloud skip, and TypeScript passed. A real PDF metadata
reference then crossed Windows Python→EGO→Nigma and stopped at
`awaiting_human_decision` with no approval or execution.

A valid 1,359-byte synthetic DOCX also crossed the running authenticated ARIA
relay, was staged with HTTP 201 and the exact OpenXML MIME type, and was then
released from EGO with HTTP 200. No synthetic source bytes remain active.

Retained environment observations: the first npm command resolved to the
Windows Hermes wrapper and was replaced by pinned WSL Node 22; the complete
Vitest run printed two non-fatal esbuild deadlock lines despite successful exit
and independent focused checks; after excluding unrelated optional peer
expansion, npm reports 21 unresolved dependency advisories (19 moderate, 2
high), for which no automatic breaking fix was applied.
