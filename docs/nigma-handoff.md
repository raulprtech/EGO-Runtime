# Nigma approved handoff

EGO 0.7.0 can consume the exact `nigma.runtime-handoff/v1` envelope created after Nigma's human approval gate. This integration is disabled by default and does not replace the regular EGO execution API.

## Responsibility boundary

Nigma selects and seals the plan, runtime snapshot, plugin snapshots, provider snapshots, bindings and permission surface. EGO owns the local policy that decides which exact hashes may be loaded and how provider identities map to private runtime configuration.

Neither the Nigma envelope nor EGO's policy contains provider credentials. `local-files@1.0.0` maps only to the `file://` scheme; the existing `LOCAL_INPUT_ROOT` realpath check remains the final filesystem boundary.

## Enable locally

```dotenv
NIGMA_HANDOFF_ENABLED=true
NIGMA_ADAPTER_POLICY_FILE=config/nigma-adapter-policy.example.json
```

The tracked example is valid only for the exact educational fixture hashes. Publish a new policy entry when a plugin or provider version changes. Duplicate identities, unknown fields, missing hashes and excessive permissions fail validation.

The runtime manifest reports the integration as configured only when both variables are present. Leaving the flag false makes the handoff endpoint return `404 NIGMA_HANDOFF_DISABLED` even when a policy path exists.

## Submit an approved invocation

```http
POST /v1/runtime/nigma/invocations
Authorization: Bearer <runtime-application-token>
Content-Type: application/json

{
  "invocation": { "...": "exact RuntimeInvocationEnvelope from Nigma" },
  "learner_context": {
    "user_id": "learner_1",
    "session_id": "session_1",
    "objective_id": "objective_1"
  }
}
```

Learner context routes runtime state but cannot change the sealed objective, input references, plugins, providers or permissions. It is included in EGO's own idempotency digest, so replaying one invocation with a different learner or session returns `409`.

EGO verifies:

- the Python-compatible canonical invocation SHA-256;
- the live approval-derived start deadline;
- exact runtime identity and version;
- exact allowlisted plugin and provider IDs plus digests;
- nested binding identities, versions, digests and permission containment;
- Nigma capabilities, runtime permissions and expected output type;
- input URI schemes allowed by the selected provider;
- EGO's ordinary capability and local/cloud artifact boundaries.

Successful submission returns `202`. Poll the ordinary `GET /v1/runtime/:invocation_id` and events endpoints. After terminal execution, retrieve a Nigma-compatible receipt:

```http
GET /v1/runtime/nigma/:invocation_id/receipt
```

The receipt preserves the exact invocation, execution and runtime-snapshot links and returns only hashed artifact references, bounded issues and metrics. Nigma validates and seals it on submission to its existing receipt endpoint.

## Authentication limitation

The Nigma envelope uses SHA-256 for integrity, not a cryptographic sender signature. The local F4.4 trust boundary therefore requires EGO's application token and a trusted local orchestrator. A remote deployment must add platform service authentication or a separately versioned signed-envelope protocol; do not expose this endpoint directly to an end-user network.

## Interoperability evidence

`tests/fixtures/nigma-handoff-v1.json` is generated by Nigma's Python implementation. EGO verifies the same canonical digest and maps it under the exact local policy. EGO's TypeScript receipt fixture is copied back to Nigma and passes its F3 conformance verifier. The full local test also reads a real Markdown file, creates four artifacts and returns a compatible receipt without cloud services.
